# Auth Guard + Admin Panel — Handoff

**Branch:** `feat/auth-guard-admin-panel` (28 commits off `develop`)
**Status:** Final whole-branch review verdict **SHIP**. Not pushed, not deployed.
**Tests:** backend 90 passing (was 47); frontend `tsc` / `eslint` / Vitest 10 clean.

## What shipped

**Phase 1 — the security fix.** The route guard decided authentication by testing whether
the `atlas_session` cookie existed. Laravel issues that cookie to unauthenticated visitors
too, so every protected page was reachable while logged out. Replaced with a server-side
`/api/v1/auth/me` check in `proxy.ts` (migrated off the deprecated `middleware.ts`), failing
closed on any error.

**Phase 2 — the admin panel.** New `Admin` Laravel module (list / detail / create / update /
deactivate / reactivate / password-reset), user deactivation enforced at login and
mid-session, lockout guardrails, an `atlas:create-admin` provisioning command, and two admin
screens.

## Two deploy-blocking bugs the final review caught

Both were invisible to per-task review — they only appear when the pieces compose.

### 1. `proxy.ts` could never authenticate anyone

It forwarded only `cookie` and `accept`. Sanctum's `EnsureFrontendRequestsAreStateful`
derives statefulness from `Referer ?: Origin`; with neither, `EncryptCookies` /
`StartSession` / `AuthenticateSession` never run and `/auth/me` 401s **despite a valid
session cookie**. The guard fails closed, so every logged-in user would have been bounced to
`/login` — a permanent login loop for 100% of users.

Verified against the real stack, one identical session cookie:

| Request shape | Result |
|---|---|
| `/me` with `Origin` (what a browser sends) | 200 |
| `/me` cookie only (what `proxy.ts` sent) | **401** |
| `/me` cookie + `Referer` (the fix) | 200 |
| `/me` cookie + `Referer` of the *internal* host | 401 |

That last row is why the fix derives the host from `x-forwarded-host`, not `request.nextUrl`
— behind Caddy, `nextUrl` is the internal host and never matches `SANCTUM_STATEFUL_DOMAINS`.
The comment in `proxy.ts` explains this; it is entirely non-obvious and should not be
deleted.

Nothing caught it earlier because browser traffic reaches Laravel through Caddy or the
Next rewrite, both of which forward `Origin`. This is the codebase's first server-to-server
authenticated call. Backend tests all use `actingAs()`, which never exercises session
resolution.

### 2. Admins were trapped in an infinite redirect loop

`RoleGuard` moved to strict `role === require`, but `(student)/layout.tsx` (redirects to
`/teacher`) and `teacher/layout.tsx` (redirects to `/dashboard`) bounced an admin between
them forever, each hop firing a fresh `/auth/me`. All three entry points — login, magic
link, invitation accept — hardcoded admin-unaware destinations, so a freshly provisioned
admin could never reach `/admin/users` except by typing the URL.

Fixed by making the pure, unit-tested `landingPathFor()` the single source of truth at every
entry point and for `RoleGuard`'s redirect target. Because each role's landing path is a
fixed point that its own guard admits, the loop is now structurally impossible rather than
patched over.

## Follow-ups, roughly by priority

1. **Bearer-token auth is unusable** (pre-existing, unrelated to this branch).
   `Laravel\Sanctum\PersonalAccessToken` never overrides `$incrementing`/`$keyType`, but this
   app's `personal_access_tokens.id` is a UUID. `createToken()` throws NOT NULL on insert, and
   the id is `(int)`-cast on read, breaking the standard `id|token` format. Harmless today —
   nothing issues tokens — but a landmine the moment a mobile client or third-party API
   access is added.
2. **The admin user list has no pagination.** It now says "Showing 25 of N" instead of
   silently truncating, but there is no way to page through. Needed once you pass ~25 users.
3. **Commit `config/octane.php`.** It is generated by `octane:install` at image build, so the
   listener list is whatever the built Octane version defaults to. The deactivation feature
   depends on `FlushAuthenticationState` (forgets guards between requests) and
   `CreateConfigurationSandbox` (clones config per request). Both are current Octane defaults
   — verified — but pinning them makes the guarantee reviewable instead of re-derived.
4. **`settings/page.tsx` renders an admin as "Student"** via pre-existing
   `role === 'teacher' ? … : …` ternaries.
5. **Two hardcoded `/dashboard` destinations remain:** `app/page.tsx` (an admin hitting `/`
   gets one redirect flash) and `useRegister.ts` (correct today — self-registration only
   produces students).
6. **Roles are written two different ways.** The admin panel uses `sync()` (exactly one
   role); `UserRepository::assignRole()` uses `syncWithoutDetaching()` (appends). A user who
   accepts an invitation while already holding a role ends up with two, after which the
   displayed role is non-deterministic while authorization sees both.
7. **13 pre-existing eslint errors** in files this branch never touched.

## A pattern worth knowing

Implementers overrode the plan's literal sample code in five separate tasks, and reviewers
backed them every time: Eloquent in the service layer (3×), a silent mass-assignment no-op on
`deactivated_at` (4×), swallowed mutation errors (2×). The plan's Global Constraints were
right; its sample code kept violating them. Well-specified constraints caught what
well-specified code did not.

## Before deploying

The fix for bug 1 is verified at the HTTP level but has not been exercised through a live
Next.js + Caddy stack. Bring up the full prod compose and confirm Caddy's actual
`X-Forwarded-Host` matches `SANCTUM_STATEFUL_DOMAINS`, then log in and confirm you are not
bounced to `/login`. That is the single highest-value pre-deploy check.

Provision the first admin with:

```
docker compose -f docker-compose.prod.yml exec api php artisan atlas:create-admin you@neoroz.com --name="Tamer"
```

Note this needs an interactive TTY for the password prompt, or pass `--password`.
